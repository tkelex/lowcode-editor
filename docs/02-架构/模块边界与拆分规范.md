# 模块边界与拆分规范

## 依赖方向

允许：

```text
apps/* -> packages/*
editor-web -> api-server HTTP API
publisher-web -> api-server public HTTP API
api-server -> Prisma -> PostgreSQL
lowcode-runtime -> lowcode-schema
```

禁止：

- app 读取另一个 app 的源码。
- `packages/*` 依赖 `apps/*`。
- 前端读取 Prisma schema、migration 或后端 service。
- 发布站读取编辑器 store、dev 物料或用户 token。
- `shared/` 反向依赖 `features/` 或 `app/`。

这些规则由 `npm run check:architecture` 执行。

## 部署单元

| 目录 | 所有权 |
| --- | --- |
| `apps/editor-web` | 编辑器静态站；自行维护 package、Vite 配置、环境变量和 Dockerfile |
| `apps/publisher-web` | Next.js 发布站；自行维护 Next 配置、环境变量和 Dockerfile |
| `apps/api-server` | API、Prisma、上传目录、后端脚本和 Dockerfile |
| `infra/docker` | 跨服务 Compose |
| `infra/nginx` | 编辑器静态资源与 API 反向代理 |
| `tests/e2e` | 跨应用 Playwright 流程 |

数据库不设独立顶层应用。Prisma schema 和 migration 由 `api-server` 所有。

## 编辑器内部

```text
app -> features -> shared
```

- `app/` 只负责装配，不承载业务规则。
- `features/<name>/api/` 保存该业务的请求函数。
- `features/<name>/types.ts` 保存该业务的接口类型。
- `features/<name>/index.ts` 是跨 feature 公开入口。
- `shared/api/http.ts` 只提供业务无关 HTTP client。
- 不创建通用 `model/` 或 `state/` 目录；使用能表达职责的文件名。
- Zustand store 使用 `stores/`，文件名表达状态职责。

跨 feature import 必须指向目标 feature 根入口，不能读取 `api/`、`components/` 或 `stores/` 深层实现。

## 编辑器核心

`features/editor/` 的边界：

- `components/`：编辑器界面与设计态 adapter。
- `materials/`：dev 物料。
- `registry/`：物料配置和 setter 元数据。
- `stores/`：组件树和运行日志状态。
- `schema/`：编辑器写入前的局部校验与 diff。
- `api/`：AI 编辑器接口。

生产物料、事件执行和无状态渲染属于 `packages/lowcode-runtime`。schema 类型、迁移、校验与生成属于 `packages/lowcode-schema`。

新增物料时至少检查：

1. editor dev 实现。
2. runtime prod 实现。
3. registry 配置。
4. schema registry 和父子关系。
5. setter 与 dev/prod prop 消费审计。

## API 内部

```text
controller -> service -> infrastructure/database
```

- Controller 处理协议和参数，不编写复杂业务规则。
- Service 执行权限、事务和领域规则。
- `ProjectAccessService` 是项目角色判断的统一入口。
- `PageLifecycleService` 拥有页面版本与发布快照完整性。
- Prisma 只在 API 部署单元内使用。
- DTO 和环境变量必须在边界处校验。

## 共享包

### lowcode-schema

- 不依赖 React、Next、Nest 或 Prisma implementation。
- 公开类型必须能被三个 app 使用。
- schema 改动要考虑迁移、校验、旧数据和测试。

### lowcode-runtime

- 接收 components、registry 和 policy，不读取应用全局状态。
- 不持久化页面，不调用 Prisma。
- 编辑器能力通过 policy 显式开启；发布策略默认最小权限。

## 文件规模与拆分

优先按职责拆分，而不是按代码类型堆积：

- 一个文件同时处理请求、状态、展示和格式化时应拆分。
- 重复实现应进入已有共享包，不能通过跨 app 深层 import 复用。
- 仅为兼容旧路径存在的 re-export 不再新增。
- 抽象必须减少真实复杂度，不能只增加目录层级。

架构检查会对超过建议行数的文件给出 warning；warning 是拆分信号，不等同于构建失败。
