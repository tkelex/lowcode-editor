# 编辑器状态订阅性能基准

本文记录 M3“Zustand 订阅收口与性能基准”的可复现方法和 2026-09-15 优化前后数据。基准用于发现无关渲染回归，不是跨设备的用户体验 SLA。

## 运行命令

```powershell
npm run benchmark:editor-state -- --sizes 500,1000 --iterations 5 --assert
```

不带 `--assert` 时只输出 JSON。断言只检查与机器速度无关的渲染范围：

- 选择节点不渲染画布节点，也不重渲染拖放订阅 probe。
- 属性、样式、撤销和重做最多渲染目标节点及两级祖先，共 3 个节点。
- 跨两个一级容器移动叶节点最多渲染移动节点、两个容器和 Page，共 4 个节点。
- 六类操作都不因 `useMaterialDrop` 的 store 订阅产生额外 render。

## 测量方法

- 使用 Playwright 启动真实 headless Chromium。
- esbuild 将真实 `EditArea`、`useMaterialDrop`、组件 registry 和 `useComponentsStore` 打入浏览器 harness。
- fixture 总节点数严格为 500 或 1000：1 个 Page、2 个一级容器，其余为叶节点。
- 每个样本前重置同一 fixture；依次测量选择、属性、样式、跨容器移动、撤销和重做。
- `actionDurationMs` 从 store action 开始计时，包含同步 React 更新；`profilerDurationMs` 是 React Profiler 在该操作内累计的 `actualDuration`。
- `nodeRenders` 由受控 dev 物料 render counter 统计；`dropTargetRenders` 由调用真实 `useMaterialDrop` 的 probe 统计。
- 每项运行 5 次并取中位数。第一轮冷启动样本保留，不人为丢弃。

## 环境

- 系统：Windows `10.0.26200 x64`
- CPU：Intel Core i9-14900HX，32 logical CPUs
- 内存：15.6 GB

## 实现结论

- `useComponentsStore` 不再有完整 store 订阅；返回对象的 selector 使用 `shallow`。
- `useComponentConfigStore` 调用统一只订阅 `componentConfig`。
- `useMaterialDrop` 只订阅稳定 action；循环/后代判断在 DnD 判定发生时读取最新组件树，因此选择和普通树更新不会让全部投放目标重渲染。
- `EditArea` 将选择态与画布树订阅拆开，递归节点使用 memo 边界。
- 属性、样式和移动采用结构共享；撤销/重做复用不可变历史树引用。未变化节点保持引用稳定，memo 才能实际跳过渲染。
